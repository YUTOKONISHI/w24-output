# リクエストとエラーのログ

要件「4. 非機能要件 ログ設計」の「APIリクエストおよびエラーログの記録」に対する計画である。
2026-08-23 時点で設計だけを決めており、**実装には着手していない。**

`20260815-requirement-gap-fixes.md` は非機能要件の3項目（Sanctum認証、REST API化、ログ設計）をまとめて「実施しない」と決めていた。
このうちログ設計だけを実施する方針に改めた。
残る2項目は据え置きで、認証は Fortify のセッション、画面は Inertia のままである。

## 現状

アプリからログを出している箇所は1つも無い。
Laravel 既定の `stack` （実体は `single`）で `storage/logs/laravel.log` に例外だけが積まれる。
ミドルウェアも `HandleInertiaRequests` があるだけで、リクエストを記録する仕組みは無い。

## 決めたこと

### 「APIリクエスト」はルートに乗る全リクエストと読む

REST API 化しない以上、記録の対象になるのは Inertia の HTTP リクエストである。
要件の「APIリクエスト」は、REST API を前提に書かれた語だが、実際に走る通信はこれしか無い。

GET も含めて全て記録する。
書き込み系だけに絞ると量は減るものの、利用者がどの画面をたどって不具合に行き着いたかを追えなくなる。

ヘルスチェック（`/up`）と Laravel Boost の開発用エンドポイント（`/_boost/*`）は除く。
前者は監視から定期的に叩かれるだけで、後者は開発時にしか存在しない。
`/build/*` の静的資産は PHP に届かないため、除外の指定は要らない。

### ファイルの専用チャンネルに出す

`config/logging.php` に `request` チャンネルを足し、`daily` ドライバで `storage/logs/request-YYYY-MM-DD.log` に出す。
保持は14日とする。

DBテーブルに残す案は採らない。
全リクエストを記録すると行が増え続けるので、古い行を消す仕組みを別に作ることになる。
`daily` ならローテーションは Laravel が持っており、DB設計の正本（drawSQL）にも影響しない。

エラーは既存の `laravel.log` のままにする。
Laravel が例外を自動で記録する経路をそのまま使い、記録の有無ではなく文脈の不足だけを補う。

### 記録する項目

| 項目 | 備考 |
|---|---|
| `method` / `path` | |
| `status` | 応答のステータスコード |
| `duration_ms` | `LARAVEL_START` からの経過。HTTP を経由しないテストでは定義されないので `null` に倒す |
| `user_id` / `guard` | 下記 |
| `ip` | |
| `input` | 下記 |

ログのレベルはステータスで振り分ける。
500番台を `error`、400番台を `warning`、それ以外を `info` にすると、失敗だけを取り出せる。

利用者の特定に `Auth::id()` を使わない。
既定ガードの `web` しか見ないため、管理画面のリクエストが匿名として残る。
`web` と `admin` を順に見て、最初に一致したガードの名前と ID を書く。
同じ判定を例外の文脈でも使うので、小さなクラスに切り出して両方から呼ぶ。

### 入力は鍵を伏せて記録する

`password`、`password_confirmation`、`current_password`、`temporary_password`、`token`、`_token` の値を `[FILTERED]` に置き換える。
入れ子になった配列も再帰的にたどる。

記録しない案も検討したが、不具合の再現には何を送ったかが要る。
伏せる鍵の指定漏れがそのまま漏洩になるため、鍵の一覧は1箇所に置いて、追加のたびにそこだけを見る形にする。

仮パスワードの発行（`PasswordResetController::sendTemporaryPassword`）は、生成した値をリクエストで受け取らないので入力には現れない。
ファイルの送信は現状どの画面にも無く、`UploadedFile` の扱いは決めていない。

### 記録は応答を返した後に行う

ミドルウェアの `handle` ではなく `terminate` で書く。
`handle` の中で `$next($request)` の後に書くと、ファイルへの書き込みが利用者の待ち時間に乗る。
`terminate` は応答を返し終えてから走るので、記録の分だけ画面が遅くなることがない。

グローバルミドルウェアとして登録する。
`web` グループに付けると、グループの外にあるルートが記録されない。

## 実装するときに触るもの

| ファイル | 変更 |
|---|---|
| `config/logging.php` | `request` チャンネルの追加 |
| `.env.example` | 保持日数の環境変数 |
| `app/Http/Middleware/LogRequest.php` | 新規。`terminate` で記録する |
| `app/Support/LogContext.php` | 新規。ログインしている主体をガード込みで返す |
| `bootstrap/app.php` | ミドルウェアの登録と、`$exceptions->context()` での文脈の追加 |

`$exceptions->context()` はコンソールの実行でも呼ばれる。
スケジューラから出た例外に `path` を書くと `/` になって誤解を招くので、`runningInConsole()` のときは何も足さない。

## 検証

`composer ci:check` に加えて、次を確認する。

- 画面を1つ開くと `storage/logs/request-*.log` に1行増え、`user_id` と `guard` が入っていること
- 管理画面のリクエストで `guard` が `admin` になること
- ログイン（`POST /app/login`）の `input` で `password` が `[FILTERED]` になっていること
- 存在しないパスを叩くと `warning` で残ること
- `/up` が記録されないこと

## 対象外

- **ログの閲覧画面**。要件は記録までしか求めていない。ファイルを直接読む
- **外部のログ基盤への転送**。デプロイ先が未定である
- **SQLクエリの記録**。件数と実行時間の調査が要る場面が来た時点で起票する
